# 입력 검증 버그 명세

기준일: 2026-10-12 (Asia/Seoul). [관리 가이드·ID 대장](bugs.md)

## 유형 설명과 작성 규칙

잘못된 입력 수용과 올바른 입력 거부를 모두 다룬다. 빈 문자열/공백/길이 경계와 프론트·백엔드 검증을 따로 기록한다. 저장 성공과 재조회 값을 구분한다.

공통 기본 정보·10개 절과 입력값/규칙/경계/잘못된 입력 수용/올바른 입력 거부/프론트·백엔드 차이/저장 후 상태를 기록한다. 아래 V1~V5는 기존 validation.ts 원본을 변환한 **과거 사례·현재 미구현**이다. 현재 기능에 구현됐거나 실제 검증됐다는 의미가 아니다. Checkout, /account, ResetPassword, /signup은 출처 경로이며 현재 사이트 경로로 사용하지 않는다.

## V1: 주문 이메일 형식 검증 누락

### 기본 정보

| 항목 | 값 |
|---|---|
| Bug ID | V1 |
| 제목 | 주문 이메일 형식 검증 누락 |
| 유형 | validation |
| 증상 분류 | false_result |
| 구현 상태 | 미구현 |
| 대상 기능 | Checkout (과거 프로젝트) |
| 발생 위치 | 과거 /checkout; src/pages/Checkout.tsx |
| 수정 파일 | 없음 — 실제 코드 변경 전 |
| 과거 프로젝트 ID | BUG-001; 과거 V3 |

### 1. 버그 개요

형식이 잘못된 이메일로 주문이 접수되는 과거 사례다.

### 2. 정상 기대 동작 (Expected Behavior)

invalid-address는 이메일 형식 오류로 거부하고 주문을 생성하지 않는다. 유효한 이메일은 다른 조건 충족 시 허용한다.

### 3. 결함 동작 (Actual Defective Behavior)

invalid-address를 수용하여 주문을 생성한다.

### 4. 재현 조건 (Preconditions)

과거 Checkout과 주문 저장 환경, 정상 상품/배송/기타 필수 입력. 현재 프로젝트에는 해당 주문 기능이 확인되지 않았다.

### 5. 재현 절차 (Steps to Reproduce)

1. 과거 /checkout을 연다.
2. 다른 필수값을 정상 입력하고 이메일에 invalid-address를 넣는다.
3. 제출하고 오류·응답·주문 상태를 확인한다.
4. 유효한 이메일과 대조한다.

### 6. 예상 관찰 결과

예상: 형식 오류 안내 없이 주문이 생성됨. 상태 확인 필요하며 HTTP 오류는 필수 증상 아님.

### 7. 버그 구현 방법

계획(과거 사례): Checkout의 이메일 형식 검증을 누락시키되 다른 필수 검증은 유지한다. 현재 적용 대상·파일은 미확정.

### 8. 탐지 방법

기존 needs: ui_validity, order_state. 입력 유효성 규칙과 저장 상태 비교가 필요하다. 과거 detectable=false를 확정 불가능 판정으로 계승하지 않는다.

### 9. 검증 기준

Baseline에서는 결함이 없어야 한다. 주입 버전에서는 위 절차로 재현되어야 한다. 의도하지 않은 추가 결함과 다른 기능의 불필요한 영향이 없어야 한다. 같은 초기 데이터·계정·환경에서 비교한다. 과거 정상 입력/기타 필수 규칙도 함께 대조한다. 현재 기능으로 적용할 때에는 계약과 격리 데이터를 먼저 확정한다.

### 10. 검증 결과

미실행 — 현재 미구현. 과거 설명은 기대되는 결함이며 이번 실행 결과가 아니다. 검증 일자·테스트·구현 커밋 없음.

### 1. 버그 개요

공백 이름이 검증을 통과한 뒤 저장 단계의 trim으로 빈 이름이 되는 과거 사례다.

### 2. 정상 기대 동작 (Expected Behavior)

이름을 trim한 결과가 빈 문자열이면 거부하고 기존 이름을 보존한다.

### 3. 결함 동작 (Actual Defective Behavior)

스페이스 3개를 검증에서 수용하고 저장 시 trim하여 재조회 이름이 빈 값이 된다.

### 4. 재현 조건 (Preconditions)

과거 로그인 계정, 기존 정상 이름, /account와 프로필 저장·조회 환경. 현재 Settings에 적용하려면 별도 계약 대조가 필요하다.

### 5. 재현 절차 (Steps to Reproduce)

1. 과거 로그인 후 /account를 연다.
2. 이름에 스페이스 3개를 입력하고 저장한다.
3. 저장 결과와 재조회 값을 확인한다.
4. 새로고침하고 이름이 빈 값인지 확인한다.

### 6. 예상 관찰 결과

예상: 성공 처리되지만 조회 이름은 빈 문자열. 원시 공백 검증과 정규화 저장 값의 차이가 핵심이다.

### 7. 버그 구현 방법

계획(과거 사례): 검증에는 trim 전 원시 이름을 전달하고 저장 trim은 유지한다. 기존 behavior의 accountNameForValidation 근거를 보존한다. 현재 변경 없음.

### 8. 탐지 방법

기존 needs: state_comparison. 전후 이름과 저장/재조회 비교가 필요하며 HTTP 성공 자체로는 탐지 불충분하다. Console 오류는 기대하지 않는다.

### 9. 검증 기준

Baseline에서는 결함이 없어야 한다. 주입 버전에서는 위 절차로 재현되어야 한다. 의도하지 않은 추가 결함과 다른 기능의 불필요한 영향이 없어야 한다. 같은 초기 데이터·계정·환경에서 비교한다. 과거 정상 입력/기타 필수 규칙도 함께 대조한다. 현재 기능으로 적용할 때에는 계약과 격리 데이터를 먼저 확정한다.

### 1. 버그 개요

새 암호와 확인값이 달라도 첫 암호로 재설정되는 과거 사례다.

### 2. 정상 기대 동작 (Expected Behavior)

확인값 불일치는 오류로 거부하고 기존 암호를 유지한다.

### 3. 결함 동작 (Actual Defective Behavior)

불일치를 수용하여 첫 번째 암호 FirstPass!123으로 변경한다.

### 4. 재현 조건 (Preconditions)

과거 재설정 흐름, 만료되지 않은 새 유효 링크, 테스트 계정의 기존 암호. 현재 ResetPassword 기능/경로가 있다고 가정하지 않는다.

### 5. 재현 절차 (Steps to Reproduce)

1. 과거 새 유효 재설정 링크를 연다.
2. 새 암호 FirstPass!123, 확인값 OtherPass!456을 입력한다.
3. 제출하고 오류/성공 안내를 확인한다.
4. 로그아웃 상태에서 FirstPass!123으로 로그인 가능한지 확인한다.

### 6. 예상 관찰 결과

예상: 불일치 안내 없이 재설정 성공하고 첫 암호 로그인 가능. 기존 암호 보존 여부도 대조한다.

### 7. 버그 구현 방법

계획(과거 사례): 확인값 일치 검사만 제거하고 첫 암호를 저장한다. 링크 만료·암호 강도 검증은 보존한다. 현재 적용 대상 미확정.

### 8. 탐지 방법

기존 needs: ui_error, subsequent_login. 오류 안내 상태와 후속 로그인 결과의 시나리오 비교가 필요하다. 실제 암호/토큰은 증거에 노출하지 않고 테스트 값만 사용한다.

### 9. 검증 기준

Baseline에서는 결함이 없어야 한다. 주입 버전에서는 위 절차로 재현되어야 한다. 의도하지 않은 추가 결함과 다른 기능의 불필요한 영향이 없어야 한다. 같은 초기 데이터·계정·환경에서 비교한다. 과거 정상 입력/기타 필수 규칙도 함께 대조한다. 현재 기능으로 적용할 때에는 계약과 격리 데이터를 먼저 확정한다.

미실행 — 현재 미구현. 과거 설명은 기대되는 결함이며 이번 실행 결과가 아니다. 검증 일자·테스트·구현 커밋 없음.

### 2. 정상 기대 동작 (Expected Behavior)
