# 기능적 버그 명세

기준일: 2026-10-12 (Asia/Seoul). [관리 가이드·ID 대장](bugs.md)

## 유형 설명과 작성 규칙

버튼 무반응, 중복 제출, 수정 후 일부 상태 미갱신, 성공 메시지와 실제 결과 불일치, 일부 동작 누락을 다룬다. HTTP 성공만으로 기능 성공을 판정하지 않고 저장·재조회·UI를 함께 비교한다.

공통 기본 정보·10개 절을 빠짐없이 작성한다. 미확정 항목은 미확정으로, 적용되지 않는 항목은 근거와 함께 해당 없음으로 쓴다. 구현 전 계획/예상과 실제 검증을 구분한다. 예시는 모두 미구현이며 현재 정답 집합에 포함되지 않는다.

유형별 추가 확인 항목: 사용자 동작, 서버 처리 여부, 데이터 변경 여부, UI와 실제 상태의 일치 여부, 중복 실행 가능성.

## F2: 보낸 메일이 수신자에게 전달되지 않음

### 기본 정보

| 항목 | 값 |
|---|---|
| Bug ID | F2 |
| 제목 | 보낸 메일이 수신자에게 전달되지 않음 |
| 유형 | functional |
| 증상 분류 | partial |
| 구현 상태 | 구현 |
| 대상 기능 | Email 내부 송수신 |
| 발생 위치 | `POST /api/mail/send` |
| 수정 파일 | `backend/mail.py` |
| 과거 프로젝트 ID | 없음 |

### 1. 버그 개요

보낸 사람의 보낸편지함에는 남고 응답도 성공이지만, 수신자의 받은편지함에
사본이 만들어지지 않는다.

### 2. 정상 기대 동작

등록된 계정으로 보내면 발신자의 보낸편지함에 1건이 남고, 수신자의
받은편지함에 읽지 않은 상태로 1건이 도착한다.

### 3. 결함 동작

발신자 쪽은 모두 정상이고 수신자의 받은편지함만 비어 있다.

### 4. 재현 조건

서로 다른 브라우저 컨텍스트 두 개(일반 창·시크릿 창). 테스트 계정 alice·bob.
쿠키는 포트를 구분하지 않으므로 같은 호스트의 다른 포트를 한 창에서 함께
쓰지 않는다.

### 5. 재현 절차

1. 창 A 에서 alice 로, 창 B 에서 bob 으로 로그인한다.
2. 창 A 에서 Email → New mail 로 `bob@adminator.test` 에게 보낸다.
3. 창 A 의 보낸편지함에 그 메일이 있는지 확인한다.
4. 창 B 의 받은편지함을 새로고침한다.

### 6. 예상 관찰 결과

3 번은 정상이고 4 번에서만 차이가 난다. 발송 응답은 201 이고 본문의
`status` 는 `delivered-internal` 이다.

### 7. 버그 구현 방법

수신함 사본을 만드는 반복문에 "자기 자신에게 보낸 경우 사본을 만들지
않는다" 는 조건을 넣되 비교를 뒤집었다. 남에게 보내면 사본이 생기지 않고
자기에게 보낼 때만 생긴다. 발신 레코드·응답·멱등 처리는 건드리지 않았다.

### 8. 탐지 방법

상태 불변 검사·오류 수집으로는 걸리지 않는다. 발송과 수신이 서로 다른
세션이라 한 트레이스 안에 어긋남이 없다. 발송 뒤 수신자 계정으로 받은편지함을
조회하고 "보낸 메일은 수신자에게 도착해야 한다" 는 기대를 적용해야 한다.
세션 두 개를 엮는 능력이 필요하다.

### 9. 검증 기준

Baseline 에서는 받은편지함에 1건이 도착해야 한다. 주입 버전에서는 0건이어야
한다. 보낸편지함·발송 응답·다른 메일 기능(임시저장·읽음·삭제)은 양쪽 모두
정상이어야 한다.

### 10. 검증 결과

2026-10-14 실행. Baseline 8002 / 주입 8000, 같은 계정·같은 절차.

| | Baseline | 주입 |
|---|---|---|
| 발송 응답 | 201 | 201 |
| 수신자 받은편지함 | 1건 | **0건** |

### 유형별 추가 확인

| 항목 | 값 |
|---|---|
| 사용자 동작 | 메일 1회 발송 |
| 서버 처리 여부 | 요청 처리됨. 발신 레코드 생성 |
| 데이터 변경 여부 | 발신자 행만 생성, 수신자 행 없음 |
| UI 와 실제 상태의 일치 여부 | 발신자 화면은 일치, 수신자 화면만 불일치 |
| 중복 실행 가능성 | 반복해도 수신 0건. duplicate 결함 아님 |

## F3: 채팅 메시지가 보낸 사람에게만 보임

### 기본 정보

| 항목 | 값 |
|---|---|
| Bug ID | F3 |
| 제목 | 채팅 메시지가 보낸 사람에게만 보임 |
| 유형 | functional |
| 증상 분류 | partial |
| 구현 상태 | 구현 |
| 대상 기능 | Chat 실제 계정 모드 |
| 발생 위치 | `GET /api/chat/rooms/{room_id}/messages` |
| 수정 파일 | `backend/resources.py` |
| 과거 프로젝트 ID | 없음 |

### 1. 버그 개요

같은 방의 참가자가 서로의 메시지를 보지 못한다. 각자 자기가 보낸 것만
보이므로 혼자 쓰는 메모처럼 동작한다.

### 2. 정상 기대 동작

공유 방의 참가자는 누가 보냈든 같은 메시지 목록을 본다.

### 3. 결함 동작

각 참가자에게 자기 발신 메시지만 반환된다. 전송은 201 로 성공하고 상대
화면에 나타나지 않는다.

### 4. 재현 조건

브라우저 컨텍스트 두 개. alice·bob 모두 Chat 에서 `Switch to real account
chat` 으로 실제 모드로 전환해야 한다.

### 5. 재현 절차

1. 창 A(alice)에서 Chat → 실제 모드 → bob 을 검색해 방을 연다.
2. 창 A 에서 메시지를 보낸다.
3. 창 B(bob)에서 같은 방을 열고 메시지를 보낸다.
4. 양쪽 화면의 메시지 개수를 센다.

### 6. 예상 관찰 결과

각 창에서 자기 메시지 1건만 보인다. 전송 응답은 201 이고 WebSocket 연결도
정상이다.

### 7. 버그 구현 방법

메시지 조회 쿼리에 발신자 필터를 남겼다. "내 메시지" 조회를 복사해 쓰면서
`sender_id == user.id` 조건이 지워지지 않은 형태다. 전송·읽음·방 목록은
건드리지 않았다.

### 8. 탐지 방법

각 세션의 응답은 그 자체로 정상이다. 같은 방을 두 참가자가 조회해 목록을
대조해야 드러난다. 한 참가자만 보면 "아직 답이 없다" 와 구분되지 않는다.
참가자가 여럿인 방에서 발신자가 모두 동일하다는 통계적 신호는 남지만,
방마다 참가자 수가 다르고 실제로 한 사람만 말한 방도 있어 단독 근거로는
약하다.

### 9. 검증 기준

Baseline 에서는 두 참가자가 같은 목록(2건)을 봐야 한다. 주입 버전에서는
각자 1건이어야 한다. 전송·읽음 표시·방 생성·참가자 권한은 양쪽 모두
정상이어야 한다.

### 10. 검증 결과

| | Baseline | 주입 |
|---|---|---|
| bob 이 보는 메시지 | 2건 (alice·bob) | **1건 (bob 만)** |
| 전송 응답 | 201 | 201 |

| 데이터 변경 여부 | 메시지 행은 정상 생성 |

## F4: 대시보드 '오늘 일정'이 UTC 기준으로 묶임

### 기본 정보

| 항목 | 값 |
|---|---|
| Bug ID | F4 |
| 제목 | 대시보드 '오늘 일정'이 요청한 시간대를 무시하고 UTC 기준으로 묶임 |
| 유형 | functional |
| 증상 분류 | false_result |
| 구현 상태 | 구현 |
| 대상 기능 | Dashboard 오늘/다가오는 일정 |
| 발생 위치 | `GET /api/dashboard` |
| 수정 파일 | `backend/resources.py` |
| 과거 프로젝트 ID | 없음 |

### 1. 버그 개요

요청한 시간대(`timezoneName`)로 변환은 하면서 "오늘" 의 경계만 UTC 로
계산한다. Asia/Seoul 기준 00:00~09:00 일정이 오늘에서 빠지고, 다음 날
같은 구간이 오늘로 들어온다. 일정 개수는 맞고 분류만 틀리다.

### 2. 정상 기대 동작

`timezoneName=Asia/Seoul` 로 조회하면 오늘 00:00~24:00(KST) 에 걸친 일정만
`todayEvents` 에 들어간다.

### 3. 결함 동작

경계가 9시간 밀려, 내일 새벽 01:00(KST) 일정이 오늘로 분류된다.

### 4. 재현 조건

alice 로 로그인. 한국시간 00:00~09:00 구간에 일정이 하나 필요하다. 낮
시간대 일정으로는 차이가 나지 않는다.

### 5. 재현 절차

1. Calendar 에서 **내일 01:00** 에 일정을 만든다(제목 `내일새벽`).
2. Home 으로 이동한다.
3. 오늘 일정 목록을 확인한다.

### 6. 예상 관찰 결과

Baseline 에서는 오늘 목록에 없고, 주입 버전에서는 들어 있다. 반대로 오늘
01:00 일정을 만들면 Baseline 에는 있고 주입 버전에서는 빠진다.

### 7. 버그 구현 방법

`datetime.now(zone)` 을 `datetime.now(timezone.utc)` 로 바꿨다. 이후 경계
계산과 비교는 그대로 두었으므로 개수·정렬·다가오는 일정 로직은 변하지
않는다.

### 8. 탐지 방법

**규칙만으로 판정된다.** 응답이 `timezone: "Asia/Seoul"` 과 각 일정의
`start`(오프셋 포함)를 함께 싣기 때문에, `todayEvents` 의 모든 `start` 가
명시된 시간대 기준 오늘 안에 있는지 검사하면 끝난다. 바깥 지식이 필요
없다.

이 결함은 **도달 능력만 재는 대조군**이다. 로그인 → 일정 생성 → 대시보드
세 단계를 밟으면 판정은 자동으로 된다. 이것을 못 잡으면 F2·F3·F5 의
0건은 판정 실패가 아니라 도달 실패로 해석해야 한다.

### 9. 검증 기준

Baseline 에서는 내일 새벽 일정이 오늘 목록에 없어야 한다. 주입 버전에서는
있어야 한다. `eventCount`·`upcomingEvents`·달력 화면·일정 CRUD 는 양쪽
모두 정상이어야 한다.

### 10. 검증 결과

| | Baseline | 주입 |
|---|---|---|
| 오늘 목록 | `[]` | **`['내일새벽']`** |
| 응답의 timezone | Asia/Seoul | Asia/Seoul |
| 해당 일정의 start | — | `2026-10-15T01:00:00+09:00` |

## F5: 메일 검색이 제목만 보고 본문을 보지 않음

### 기본 정보

| 항목 | 값 |
|---|---|
| Bug ID | F5 |
| 제목 | 메일 검색이 제목만 보고 본문을 보지 않음 |
| 유형 | functional |
| 증상 분류 | partial |
| 구현 상태 | 구현 |
| 대상 기능 | 통합 검색(Search work) |
| 발생 위치 | `GET /api/search` 의 mail 분기 |
| 수정 파일 | `backend/service_hub.py` |
| 과거 프로젝트 ID | 없음 |

### 1. 버그 개요

검색 조건에서 본문이 빠져 제목만 훑는다. 본문에만 있는 단어로는 메일을
찾지 못한다. 다른 종류(일정·할 일·채팅)는 정상이다.

### 2. 정상 기대 동작

제목 또는 본문에 검색어가 있으면 결과에 나온다.

### 3. 결함 동작

제목에 있으면 나오고 본문에만 있으면 0건이다. 결과 목록의 형식과 본문
발췌는 정상이라 다른 종류와 구분되지 않는다.

### 4. 재현 조건

alice 로 로그인. 제목과 본문에 서로 다른 단어가 들어간 메일이 1건 필요하다.

### 5. 재현 절차

1. 제목 `회의록`, 본문 `분기 예산 검토 건입니다` 로 메일을 보낸다.
2. 헤더의 `Search work` 를 연다.
3. `예산` 으로 검색한다(본문에만 있는 단어).
4. `회의록` 으로 검색한다(제목에 있는 단어).

### 6. 예상 관찰 결과

3 번은 0건, 4 번은 1건이다. 두 요청 모두 200 이고 결과 형식도 정상이다.

### 7. 버그 구현 방법

공통 `add()` 헬퍼가 제목과 본문을 합쳐 검사하므로, mail 분기만 헬퍼를
거치지 않고 제목에 대해서만 조건을 걸었다. 결과에 담는 발췌는 본문
그대로 두어, 응답만 보고는 본문이 검색에서 빠졌는지 알 수 없다.

### 8. 탐지 방법

0건은 그 자체로 정상 상태이므로 오류·상태 불변 검사에 걸리지 않는다.
결과의 `text` 필드가 다른 종류와 똑같이 채워지므로 형식 비교로도 드러나지
않는다. 그 메일 본문에 검색어가 있다는 사실을 알아야 0건이 틀렸다고
판정할 수 있다. 메일을 먼저 만들고 그 내용을 기억하는 흐름이 필요하다.

### 9. 검증 기준

Baseline 에서는 본문 단어로 1건이 나와야 한다. 주입 버전에서는 0건,
제목 단어로는 여전히 1건이어야 한다. 일정·할 일·채팅 검색과 검색 상한·
페이징은 양쪽 모두 정상이어야 한다.

2026-10-14 실행. `GET /api/search?kind=mail`.

|---|---|---|
| `예산` (본문) | 1건 | **0건** |
| `회의록` (제목) | 1건 | 1건 |
| 결과의 text 필드 | 채워짐 | 채워짐 |
