기준일: 2026-10-12 (Asia/Seoul). 웹 테스트 에이전트의 결함 탐지 능력을 평가하는 샘플 웹사이트의 명세 기준이다. **이번 작업은 문서 표준화만 수행했다. 실제 버그 주입·기능 코드·DB·런타임 변경·브랜치 생성/병합은 수행하지 않았다.**

## 목적과 현재 단계

정상 동작하는 협업 사이트를 Baseline으로 보존하고, 향후 Git의 개별 브랜치에서 소스에 결함을 직접 구현한다. 결함 버전 탐색 결과를 평가자용 Markdown Ground Truth와 대조한다. 정상 Baseline이라는 명칭은 평가 기준 역할이며 운영 환경의 무결함을 보장하지 않는다. 기존 QA 이슈와 의도적 주입 명세는 별개다.

브랜치는 `main`(Baseline, `ccd7fcf`)과 유형별 결함 브랜치로 나눈다. `funtional` 브랜치에 기능 결함 4건(F2~F5), `routing` 브랜치에 이동·라우팅 결함 4건(N2~N5)을 구현했고, 각각 Baseline 과 대조해 검증한 수치를 유형 문서의 검증 결과에 적었다. 결함은 브랜치에 직접 구현하며 환경변수로 끄지 않는다. 각 결함 브랜치는 `GET /api/bugs` 와 `GET /gt.json` 을 제공해 평가자가 어느 버전이 떠 있는지 확인할 수 있게 한다. 이 두 엔드포인트는 검사 대상 모델에 제공하지 않는다. F1/N1/U1은 작성 예시, V1~V5는 이전 프로젝트 사례이며 모두 미구현이다. 향후 Baseline의 정확한 커밋 SHA와 배포·데이터 버전은 실제 구현 시작 전 기록한다.

## 공통 명세 작성 규칙

모든 유형은 기본 정보와 다음 10개 절을 사용한다. 유형별 파일의 복사 가능한 템플릿이 동일 구조를 제공한다.

기본 정보: **Bug ID, 제목, 유형, 증상 분류, 구현 상태, 대상 기능, 발생 위치, 수정 파일**. 과거 ID·출처는 별도 필드다. 발생 위치는 사용자 페이지/컴포넌트/API이고 수정 파일은 실제 변경 경로다. 구현 전 수정 파일은 `없음`으로 쓰고 후보 경로는 구현 계획에 둔다.

1. 버그 개요: 기능·결함·영향 범위.
2. 정상 기대 동작: Baseline에서 확인할 결과.
3. 결함 동작: 주입 후 발생해야 할 결과.
4. 재현 조건: 계정/권한, 초기 데이터, 환경, 시작 화면.
5. 재현 절차: 순서·입력값·사용자 동작·확인 지점.
6. 예상 관찰 결과: 화면·응답·저장 상태의 구체적 차이.
7. 버그 구현 방법: 계획과 실제 변경을 구분하고 구현 후 커밋·경로 연결.
8. 탐지 방법: 수단·예상 근거·한계, 규칙 검사/상태 비교/의미적 판단 구분.
9. 검증 기준: Baseline 정상, 주입 재현, 추가 결함 없음, 영향 최소화.
10. 검증 결과: 일자·환경·테스트·증거·커밋·통과/실패/미실행.

| 증상 값 | 의미 |
|---|---|
| no_response | 동작 후 반응 없음 |
| partial | 처리 일부 누락 또는 상태 일부 미갱신 |
| false_result | 성공/실패 표시 또는 판정과 실제 결과 불일치 |
| duplicate | 같은 동작 중복 실행 |
| wrong_target | 잘못된 대상/목적지 |
| visual | 화면 모양·표시 오류 |

유형과 증상은 서로 다른 축이다. 구현 상태는 `미구현 → 구현 중 → 구현 완료 → 검증 완료`로 관리한다. 실패나 미실행이면 검증 완료로 올리지 않는다. 통합 커밋이 바뀌면 이전 검증의 범위를 유지하되 새 조합은 재검증 대기로 기록한다. 미구현 항목의 관찰·탐지 설명은 예상이며 실제 결과를 꾸며 쓰지 않는다. 기존 detectable boolean 대신 예상 탐지 수단과 판단 근거를 기록한다.

## Git 기반 구현·병합·회귀 절차

다음은 **향후 절차**이며 이번 작업에서 실행하지 않았다. 실제 branch/status/dirty 변경과 Baseline 커밋을 먼저 확인한다. 기존 브랜치 삭제·reset·사용자 변경 덮어쓰기를 하지 않는다.

```text
main 또는 합의된 정상 Baseline (정확한 SHA 기록)
  +-- bug/F1
  +-- bug/V1
  +-- bug/N1
  +-- bug/U1
         → 별도 통합 브랜치에서 병합·전체 재현 검증
```

브랜치 이름은 예시다. 작업 환경의 기본 `codex/` 접두사를 쓰면 `codex/bug/F1`로 만들 수 있다. 한 브랜치에는 가급적 한 명세만 구현하고 정상 로직의 최소 부분만 변경한다. 기준 버전에서 먼저 기대 동작을 검증한 뒤 소스에 직접 결함을 구현한다. 문서의 수정 파일·구현 방법·상태를 실제 변경에 맞추고 구현 커밋을 ID로 연결한다(예: `F1: 일정 저장 버튼 무반응`). 명세 갱신 커밋에서도 구현 SHA를 기록한다.

개별 주입 버전에서 재현 및 주변 기능 회귀를 수행한다. 같은 파일을 수정하는 버그는 사전 영향 범위를 비교한다. Git 충돌 해결만으로 완료하지 않고 가드·이벤트·DOM·저장 규칙의 논리 충돌을 검사한다. 통합 후 **포함된 모든 버그**를 같은 명세 절차로 다시 검증하고 추가 결함·기능 영향·조합 의존성을 기록한다. 개별 버그 검증을 통합 검증으로 대체 인용하지 않는다.

정상/결함 버전은 Git SHA·빌드/배포 코드로 구분한다. DB와 테스트 데이터는 Git과 별도 관리하며 각 버전에 동일 초기 fixture 사본을 제공한다. 개발 DB reset/migration을 버그 검증에 사용하지 않는다. Baseline 복귀는 해당 코드와 격리 데이터 사본을 사용하는 방식이다.

관련 테스트는 [검증 안내](../docs/TESTING.md)와 package.json의 현재 명령에 맞춘다. 변경 영역의 단위/API/브라우저 검증과 통합 회귀를 수행한다. 현재 사이트는 JS/FastAPI이므로 과거 프로젝트의 tsconfig 검사 명령을 전제하지 않는다. 빌드는 기존 dist를 정리하므로 보존/별도 출력 절차를 먼저 따른다.

## Ground Truth와 노출 방지

Ground Truth는 평가자·개발자만 사용하는 이 문서와 유형별 명세다. 평가 실행별 비공개 목록에 실제 포함된 ID, Baseline/주입/통합 SHA, 빌드·데이터 버전, 발생 위치, 조건·절차, 기대/결함 동작, 탐지 수단, 검증 결과를 고정한다. 예시와 미구현 항목은 실행의 정답 집합에 포함하지 않는다. 에이전트 보고와 ID 매칭 근거·중복 보고·미탐지·명세 밖 관찰을 기록하고 예상 탐지 여부를 실제 탐지 결과로 오인하지 않는다.

현행 방식에는 환경변수 버그 ON/OFF, BUGS_ON/BUG_F1, isOn/useBug 분기, 활성화 관리자 UI, 런타임 토글, 활성 버그 API(`/api/bugs`), 공개 정답지(`/gt.json`), 버그 상태별 동적 CSS가 없다. 기존 원본의 이런 설계는 과거 참고로만 보존한다. 자동 생성 API/서버를 새로 만들지 않는다.

### 2026-10-12 정적 노출 점검

- Webpack entry/context는 `src`, 정적 제공은 개발 `src`/preview `dist`다. copyPlugin은 `src/assets/static`만 복사한다. `bugDocs`는 경로 밖이며 import/복사 참조를 발견하지 못했다.
- FastAPI `backend/config.py`의 기본 static_dir는 `dist`다. `backend/app.py`는 해석된 경로가 static root 내부인지 확인한 뒤 파일을 제공한다. 기본 설정에서 저장소 루트의 `bugDocs`는 제공 범위 밖이다.
- 기존 `dist`에서 bugDocs/명세/과거 TS 파일 포함 여부를 별도 확인한다. 저장소 루트를 정적 root로 지정하거나 문서를 dist/src에 복사하면 안 된다. HTML 인증 보호만으로 Markdown 접근이 차단된다고 가정하지 않는다.
- 이번 확인은 로컬 코드·파일 구성의 정적 점검이다. 실제 배포의 static_dir 재정의·reverse proxy·외부 문서 호스팅·HTTP 응답은 미검증이다. 평가 전 문서 URL과 과거 공개 정답지 URL을 HTTP로 확인하여 명세 내용을 반환하지 않는지 검증한다. 저장소/문서 사이트 접근 권한도 평가자 전용으로 설정하고 에이전트에 소스/문서 접근을 제공하지 않는다.
